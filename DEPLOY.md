# Hosting this app for free, with the data that's already in it

The plan, and why it's shaped this way:

| Piece | Where | Why |
|---|---|---|
| The app | **Render**, free plan, Singapore region | Free with no card. Sleeps after 15 min idle. |
| The data | **Neon**, free Postgres, Singapore | Render's free disk is wiped on every restart, so the database cannot live there. Neon's free tier doesn't expire and doesn't delete your data. |

**The one thing to know before you start:** a free Render service goes to sleep
after 15 minutes with no traffic. The next person to open it waits about 40
seconds for the first page; everything after that is normal speed. Step 7 shows
how to avoid that and stay inside the free allowance.

Total cost: nothing. No credit card at any point.

---

## 1. Create the database on Neon

1. Go to **https://neon.com** and sign up (GitHub login is fine).
2. Create a project. Name it `jsw-cf`, region **AWS Asia Pacific (Singapore)** —
   the closest free region to Delhi.
3. On the project dashboard, copy the **connection string**. It looks like:

   ```
   postgresql://jsw_cf_owner:AbC123xyz@ep-cool-name-a1b2c3.ap-southeast-1.aws.neon.tech/jsw_cf?sslmode=require
   ```

   Keep the `?sslmode=require` on the end. Paste it somewhere safe — you need it
   twice, in step 2 and step 5.

---

## 2. Push your existing data into it

This is the 302 rows sitting in `data/jsw_cf.db` right now: 24 dealers, 113
dispatches, 106 billing rows, 13 GRNs, both godowns, your opening stock, your
SAP product mappings, and your admin login.

From this folder on your Mac:

```bash
venv/bin/pip install -r requirements.txt      # picks up the new Postgres driver
venv/bin/python scripts/push_to_postgres.py \
  --target "PASTE_YOUR_NEON_CONNECTION_STRING_HERE"
```

Run it with `--dry-run` first if you want to see what it will copy without
writing anything.

It builds the tables, copies every row keeping the same ids (so every dispatch
still points at the right dealer), moves the id counters past what it inserted,
and then counts both sides back to you. You want to see `Done.` and `ok` on
every line.

Your **existing username and password still work** — the users table came across
with the rest. The `ADMIN_PASSWORD` setting only ever creates a first admin on a
completely empty database, so it is ignored here.

To redo the copy later (say you enter more data locally before going live), add
`--wipe`. Without it the script refuses to write on top of existing rows rather
than silently doubling them.

## 3. Put the code on GitHub

```bash
cd ~/Desktop/jsw_cf_app
git init
git add -A
git commit -m "JSW C&F operations app"
```

`.env` and `data/*.db` are excluded by `.gitignore`, so no passwords and no
business data go to GitHub. Worth confirming before you push:

```bash
git ls-files | grep -E "\.env$|\.db$"     # should print nothing at all
```

Then create a **private** repo on GitHub called `jsw-cf-app` and follow the two
lines GitHub shows you (`git remote add origin ...` and `git push -u origin main`).

Private matters: the repo has no secrets in it, but it does have your whole
business logic.

---

## 4. Deploy on Render

1. Go to **https://render.com**, sign up with GitHub.
2. **New +** → **Blueprint** → pick the `jsw-cf-app` repo.
3. Render reads `render.yaml` and shows you one web service on the free plan.
   **Change the service name** before you click apply — this becomes your public
   address. Don't leave it as `atc-ops`; use something nobody would type by
   accident, for example:

   ```
   atc-ops-7b799c      →  https://atc-ops-7b799c.onrender.com
   ```

4. It will ask you for the values marked "sync: false". Fill in:

   | Key | Value |
   |---|---|
   | `DATABASE_URL` | your Neon connection string from step 1 |
   | `ADMIN_USERNAME` | `admin` |
   | `ADMIN_PASSWORD` | `S*X!-%3r1u0zWyd=CKNK` (unused, see below — but don't leave it weak) |

   `SECRET_KEY` is generated by Render automatically; leave it alone.

5. Click apply. First build takes 3–5 minutes.

`ADMIN_PASSWORD` never gets used because your admin user already exists in the
database. It's there as a safety net: if the database were ever wiped, the app
would recreate an admin with that password, so it must not be `changeme123`.

---

## 5. Check it

Open your URL. You should get the login screen, and your normal username and
password should work. Check that the dispatch and billing pages show your real
rows, and that the godown switcher offers both Manesar and Daultabad.

`https://your-name.onrender.com/robots.txt` should return `Disallow: /` — that's
what keeps it out of Google.

---

## 6. Change your admin password

It's on the public internet now. Log in → Users → set a long one. A password
manager entry, not something you can type from memory.

---

## 7. Getting rid of the 40-second wait (still free)

Render gives a workspace **750 instance hours a month**. A month is 720–744
hours, so *one* service can stay awake around the clock and still fit inside the
free allowance — the sleep isn't a quota, it's just idleness.

So: create a free account at **https://cron-job.org**, add a job that requests
`https://your-name.onrender.com/login` every **14 minutes**. The app never goes
idle long enough to sleep, and mornings are instant.

Only do this for this one service. A second always-on free service puts you over
750 hours.

---

## 8. Backups

Neon keeps your data safe from its side, but nothing protects you from a bad
import or a wrong delete. The app's own **Backup** page still works and now pulls
from Postgres — download a copy weekly and keep it off the laptop.

## What changed in the code for this

Five small things, all of which leave the local SQLite setup working exactly as
before — `./run.sh` still behaves identically:

- `app/migrations.py` now returns immediately on anything that isn't SQLite. It
  is legacy upgrade code written in SQLite-only SQL (`DATETIME` columns, the
  rename-recreate-copy trick for changing a UNIQUE constraint), and a Postgres
  database is always built fresh from the models instead, so it has nothing to do
  there.
- `app/database.py` accepts the `postgresql://` string a provider hands you
  verbatim and adds the driver itself, and turns on `pool_pre_ping` +
  `pool_recycle` — serverless Postgres drops idle connections, and without this
  the first request after a quiet spell fails on a dead one.
- `requirements.txt` gained `psycopg2-binary`.
- `app/main.py` serves a `robots.txt` that disallows everything.
- `render.yaml` describes the service so Render doesn't have to be configured
  by hand.
- `scripts/push_to_postgres.py` is new — the copy tool from step 2.

All of it was tested against a real Postgres 16 before you got it: 302 rows
copied with matching counts on both sides, id sequences verified by inserting a
new row and confirming it got id 25 rather than colliding with id 1, and every
page in the app rendered from Postgres under two Gunicorn workers.
